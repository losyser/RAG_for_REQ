## 1. 研究命题

**核心命题**：用 RAG 据检索证据生成的工程需求，比"无检索、直接据需求生成"的工程需求**更可信**——更低幻觉率、更低过推断率。其余（多粒度、ranker、profile）只是辅助手段。

**可证伪判据**：若在公平、非循环的度量下，RAG 组的幻觉/过推断不显著低于无 RAG 组，则命题伪——或度量/设计有问题。

---

## 2. 整体执行逻辑（从 0 到结论）

```
原始需求(ERNIE 出题, 60条, 冻结)
        │  DeepSeek 拆分(共享, 124子需求, 冻结)
        ▼
 ┌──────────────┴──────────────┐
 │ B0 (no-RAG)        R (RAG)   │   ← 两组共用同一份子需求拆分（单变量）
 │ 据子需求生成       多粒度检索→据证据生成(无证据弃权)
 │ (Qwen)             (Qwen)
 └──────────────┬──────────────┘
        ▼ 两组工程需求(shall)
   公平可信度评估层（两组同判，破 M1 循环）
   每条 shall: DeepSeek 抽 claim → evidence_units 索引回溯 → ERNIE 判
   support/contradict/not_found；H_hard=contradict、H_soft=not_found；ERNIE 判 OI
        ▼
   按源需求聚合 → B0 vs R 配对 Wilcoxon + bootstrap CI
        ▼
   人工校准 50 条（验证裁判 + 辨别 KB漏召 vs 编造）
```

## 4. 数据构造（Phase 1）

## 5. 生成方法（Phase 3，`cooling_rag_mg/evidence_first_generator.py` + `scripts/44`）

**单变量设计**：B0 与 R 共用同一 system base，唯一差别 = R 的 user 消息注入检索证据块。

**共用 system base（`BASE_SYSTEM`）**：
```
你是船舶主机冷却水系统的需求工程师。把给定的子需求转化为结构化工程需求(shall)。
规则：
- shall_statement 用清晰工程语言书写，忠实于子需求范围，不要扩大义务。
- **无可靠依据不得编造**具体数字/阈值/标准编号；无法确认的参数写「待按厂家技术数据确认」。
- verification_method 取值之一：review/inspection/calculation/test/...
只输出 JSON：{"engineering_requirements":[{"shall_statement","verification_method","acceptance_criteria","evidence_ids"}]}
```

- **B0**：user 仅含原始需求 + 子需求，无证据块，evidence_ids=[]。永不弃权。
- **R**：user 含原始需求 + 子需求 + 证据块 + "仅依据上述证据生成、未覆盖不得编造"；evidence_ids=检索命中。无证据则弃权（不产出 shall，记入覆盖率）。
- R 的检索：复用 `run_sub_requirement_stage`（多粒度 BM25+BGE-M3+RRF+profile+applicability+DeepSeek 证据审查），取 selected_results 作证据。

**产物**：`data/search_results/main_experiment/{B0,R}_results.json`
- B0：141 ER（全 124 子需求覆盖，evidence_ids 空）。
- R：316 ER，覆盖率 89.5%（111/124 子需求有证据，弃权 13）。

## 6. 评估方法（Phase 2，`cooling_rag_mg/credibility_eval.py` + `scripts/43`）

对每条 shall：
1. `extract_claims`（DeepSeek）抽原子事实 claim。
2. 每个 claim：`kb_search`（evidence_units 索引，BM25+向量+RRF，top_k=8）召回 KB 段落 → `judge_claim_llm`（ERNIE）判 **support / contradict / not_found**。
3. `score_shall`：**H_hard = contradict 占比**（硬幻觉，被 KB 明确矛盾，与措辞无关，主指标）；**H_soft = not_found 占比**（软幻觉，KB 查无，对检索敏感）。无 claim → None 剔除。
4. `judge_over_inference`（ERNIE）：判 shall 是否超出原始需求+证据授权加义务（**OI**，与 H 正交）。
5. `aggregate_by_source`：按源需求取均值（None 剔除），配对单位=源需求。
6. `paired_compare`（grounding.py）：配对 Wilcoxon + bootstrap 95% CI。

**裁判 prompt**（claim）：
```
判断「证据」与这条事实性 claim 的关系：support/contradict/not_found。只输出 {"verdict":...}
```

## 7. 结果

### 7.1 主实验（n=59 配对源）
| 指标 | B0 | R | diff(B0−R) | p | 显著 |
|---|---|---|---|---|---|
| H_hard 硬幻觉 | 0.012 | 0.008 | +0.004 | 0.686 | ✗ |
| H_soft 软幻觉 | 0.533 | 0.435 | +0.098 | 0.022 | ✓ |
| OI 过推断 | 0.102 | 0.155 | −0.053 | 0.075 | 边缘(R更差) |

verdict 分布：support 760 / not_found 519 / contradict 9（无 API 污染）。

### 7.2 人工校准（50 条分层）
- **裁判一致率 68%**：auto 高估 contradict（9 条 auto-contradict，人工仅认 3）、高估 support（9 条 auto-support 人工改判 not_found）。
- **not_found 的本质**：B0 16 条 not_found 中 **14(88%) 是合理需求(KB漏召)**、仅 2 编造；R 19 条中 14(74%) KB漏召、5 编造。
- **真编造(claim_reasonable=n)共 10 条：B0 占 3，R 占 7**（R 误读证据，如错误生成"不应使用铜镍合金"）。

## 8. 根因审查：为什么会得到"负结果"

用户对负结果存疑，遂做端到端审查。**结论：该负结果在很大程度上是实验设计造成的假象，主要有三处。**

### 缺陷 ①（致命）：共用安全条款摁死了 B0 的数字幻觉
- **证据**：B0 的 141 条 shall **含具体数字占比 0.0%**、含带单位数值 0.0%；R 为 16.8% / 8.5%。匹配样本里 B0 全是定性表述（"应配备温度/压力传感器实现实时监测"），R 才有具体阈值/部件（HT/LT 回路等）。
- **机理**：为追求"单变量纯净"，B0 与 R 共用了含"**无依据不得编造具体数字**"的 system base。这条安全条款让 B0 **完全回避具体参数**——而幻觉的高发载体正是具体数字/阈值。B0 没去犯那个错，自然测不出"RAG 降低数字幻觉"的增益。
- **后果**：命题想检验的场景是"无 RAG 的 LLM 自信编造具体参数 → RAG 用真证据替换之"。我们的 B0 被 prompt 阉割，根本没进入这个场景。**这不是命题被证伪，而是设计没造出能检验命题的条件。**

### 缺陷 ②：H_soft 在测 KB 覆盖，不是测幻觉
- 人工校准坐实：not_found 的 ~80% 是 KB 未收录的**真实需求**（KB 漏召），不是编造。R 因"只据检索证据生成"天然只谈 KB 覆盖到的话题，故 H_soft 低——这是**覆盖/循环偏置**，非可信度。H_soft 不能作可信度结论。

### 缺陷 ③：H_hard 基率近零 → 无统计功效
- 全样本 contradict 仅 9（人工核实后仅 3）。在两组都几乎不产生"被 KB 矛盾"的硬错误时，根本没有功效去检出组间差异。而硬错误少，又是缺陷①（B0 不出具体数字）的直接后果。

### 次要：裁判噪声（一致率 68%）、源级而非子需求级配对、claim 数不对称（B0 少具体→claim 少）。

---

## 9. 修正建议（让实验能真正检验命题）

1. **B0 改为"真实无 RAG 基线"**：去掉"不得编造数字"的阉割，改为要求"生成完整、具体的工程需求（含参数/阈值）"，让 B0 像真实工程师用 ChatGPT 那样**给出具体参数（含其参数记忆里的、可能编造的）**。R 保持据证据生成。这样 B0 的编造才会暴露，KB 接地裁判才测得到 RAG 的降幻觉增益。
   - 注意单变量边界随之调整：treatment 变为"完整 RAG（检索+证据约束）" vs "无检索直接生成"，这正是用户命题的本意（整体 RAG vs 裸 LLM），而非"仅证据块"的过度纯化。
2. **以 H_hard 为主指标**，但需在 B0 会出具体数字后才有基率；H_soft 仅作覆盖描述、不作可信度结论。
3. **加可溯源正确率**：R 引证据，可查"被引证据是否真支持该 shall"（misread 检测，针对缺陷中发现的 R 误读证据问题）。
4. （可选）跨裁判（ERNIE+DeepSeek）+ 提高裁判 prompt 质量以降噪；子需求级配对子集做头条。

---

## 10. 一句话总结

当前"负结果"主要由**B0 被安全条款阉割**（数字幻觉占比 0%）+ **H_soft 实为覆盖偏置** + **硬幻觉基率近零无功效**三者造成，**不足以判定命题被证伪**。修正 B0 为真实无 RAG 基线后重测，才是对命题的公平检验。
